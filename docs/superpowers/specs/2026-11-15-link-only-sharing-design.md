# Этап8: доступ по отзываемой ссылке — уточнение требований

Статус: требования согласованы пользователем15 ноября2026, реализация разрешена.
Этот документ заменяет предложение о персональном доступе. Production-перенос
потребует отдельного согласования после локальной проверки.

## Подтверждено пользователем

- Реализовать временное открытие приглашения вставкой ссылки внутри Pickmatch.
- Убрать выдачу и отзыв доступа по имени/email: пользователь отказался от неё ранее.
- Доступ контролируется наличием ссылки, которую владелец может сбросить/отозвать.
- Автоматическое открытие через Universal Links остаётся отдельным этапом.
- Оба типа альбомов доступны участникам только по действующей ссылке автора.
- В приватном альбоме статистику видит только автор; в публичном — все допущенные по ссылке.

## Обнаруженный разрыв с существующим сервером

- Сейчас существуют разные /vote/{invite_code} и /share/{share_token} ссылки.
  Первая служит отбору, вторая открывает аналитику. Не объединять эти полномочия
  незаметно для пользователя.
- POST /albums/{id}/share-token/rotate меняет токен, но сохраняет SharedAccess.
  Поэтому ранее открывший ссылку аккаунт продолжает иметь доступ к приватным
  файлам по require_album_media_access. Это не удовлетворяет требованию отзыва.
- GET /albums/shared/{token}/analytics автоматически создаёт SharedAccess.
- Старые POST/GET/DELETE /shared/... по имени/email зарегистрированы в main.py.
  Их скрытие только в iOS не устраняет старый серверный способ выдачи доступа.
- Публичные файлы сейчас пропускаются без ссылки и авторизации. Для приватных
  существующие SharedAccess, голоса и комментарии дают разные основания доступа
  в разных маршрутах. Нужно согласовать единое правило и проверить все входы.
- Выдаваемый media ticket привязан к пользователю/файлу, но не к версии ссылки.
  Отзыв должен проверяться сервером на новых запросах файла/видео, включая Range.

## Обязательные свойства будущей реализации

- Сброс делает старую ссылку недействительной, выпускает новую; отзыв отключает
  текущую ссылку без неявного повторного создания при открытии панели владельца.
- Отзыв действует и для ранее открывавших ссылку на новых серверных запросах;
  прошлое посещение и старые персональные записи не обходят отзыв.
- Уже полученные пользователем байты и начатый ответ невозможно забрать обратно.
- Владелец сохраняет собственный доступ. Учётные JWT не заменяют проверку права
  на конкретный альбом. Старые данные голосования/комментариев не удаляются ради отзыва.
- Раздел списка полученных ссылок/альбомов, если сохраняется, не становится
  самостоятельным вечным разрешением на просмотр.
- Поведение сайта, изображений, видео, аналитики, голосования и комментариев
  учитывается в одном изменении прав. Схема/миграция, если понадобятся, additive;
  старые записи не чистятся в production без отдельного согласованного переноса.
- Работа локальная/в изоляции; production-перенос согласовывается после проверки.

## Выбранная реализация

Пользователь определил правила доступа и разрешил реализацию. Ниже технические
решения исполнителя, которые сохраняют эти правила и рабочий веб-клиент.

- Используем существующий случайный invite_code как версию основного приглашения;
  is_active означает, что внешние ссылки разрешены. Владелец доступ сохраняет.
- Внутренняя SharedAccess становится записью посещения действующей ссылки:
  добавляем nullable link_version VARCHAR(64) с SHA256(invite_code). Строка без
  версии, старый голос или комментарий не дают права на новые запросы альбома.
  Это не персональная выдача разрешений: API по имени/email уже удалён.
- Центральная функция проверяет владельца либо active+совпадение link_version;
  все чтения/записи альбома, медиа, голосов и комментариев используют её.
  Список «Доступные мне» возвращает только актуальные посещения.
- Посещение GET /albums/invite/{code} авторизованным пользователем запоминает
  текущую версию. При регистрации посещения и сбросе блокируется одна строка
  Album в PostgreSQL, чтобы конкурентный старый визит не восстановил доступ.
- Гостевой веб-просмотр по ссылке сохраняется для обоих типов: ответ содержит
  медиа-URL с ограниченным invite-параметром. UUID файла без ссылки/допуска ничего
  не открывает; на каждом новом запросе/Range проверяются код и активность.
  Голоса, комментарии и статистика по-прежнему требуют входа в аккаунт.
- Авторизованным клиентам media/access выдаёт короткий ticket для обоих типов
  альбомов; ticket участника связан с версией ссылки, чтобы повторное открытие
  новой ссылки не делало старый video ticket действительным снова.
- Старые /share/{share_token} остаются совместимым видом ссылки на альбом:
  они тоже требуют активности и запоминают ту же версию. Для приватного альбома
  ответ содержит только разрешённые фото/свои комментарии, без статистики;
  can_view_stats из старой записи не позволяет обойти это правило.
- Сброс меняет invite_code и существующий share_token в одной транзакции.
  Отзыв выключает is_active; явное повторное создание выпускает новые коды.
  Открытие панели владельца только читает состояние и не отменяет отзыв.

## Новый API владельца

- GET /albums/{id}/invitation: read-only {is_active, invite_code, invite_url};
  код/URL null при отозванном приглашении.
- POST /albums/{id}/invitation: явное создание/включение; активное приглашение
  возвращается прежним, после отзыва выпускается новый код.
- POST /albums/{id}/invitation/rotate: явный сброс обеих ссылок и прежних допусков.
- DELETE /albums/{id}/invitation: идемпотентный отзыв всех внешних ссылок.
- Старые owner share-token вызовы используют ту же блокировку/версию; получение
  legacy токена при отзыве не включает ссылки автоматически. Старые /share
  больше не предоставляют полную статистику приватного альбома.

## Нативный сценарий

У владельца в галерее — форма ссылки со стандартным ShareLink и явными
«Создать ссылку», «Сбросить ссылку», «Отозвать ссылку». Разрушающие действия
подтверждаются; неопределённый результат сверяется read-only GET, без слепого
повтора мутации. Формы открываются через item и не пишут состояние при инициализации.

У получателя — «Открыть приглашение» на главном экране, поле для полного HTTPS URL
pickmatch.site/vote/{code} или pickmatch.site/share/{token}. Парсер отвергает чужой
хост, userinfo, нестандартный порт, query/fragment, percent-encoded разделители и
лишние сегменты; код ASCII URL-safe длиной1...128. URL не используется как API origin.
Получатель входит до открытия приглашения в iOS. Код не пишется в логи/на диск.

Списки своих и доступных альбомов независимы; чужой альбом не вставляется в свои.
Общая галерея и MediaViewer читают одни метаданные из двух коллекций SessionModel;
отдельная дублирующая модель деталей не нужна. Все новые запросы ограждены
session.mediaRevision; выход чистит формы, метаданные и медиа.403/404 при обновлении
очищает недоступный альбом/просмотр; временная сеть сохраняет ранее разрешённые данные.
iOS-голосование и экран статистики остаются следующими этапами; сервер/веб уже
соблюдают согласованные права для этих функций.

## Проверки и перенос

Проверить владельца/актуального посетителя/чужого пользователя/старую персональную
запись/старые голоса и комментарии/гостя с кодом и без него для обоих типов.
Проверить сброс, отзыв и повторное создание для старого URL, записи посещения,
ticket и video Range; открытие новой ссылки не оживляет старый ticket. Приватная
статистика не выдаётся через ID, /share, старый can_view_stats или публичный
альбом после смены приватности. История и пользовательские данные не удаляются.

Миграция только добавляет nullable поле с проверкой существования и без очистки
старых строк. Старые допуски теряют силу до нового входа по актуальной ссылке.
Проверить SQLite и отдельный локальный PostgreSQL; Cloudinary не нужен для
проверки разрешений. Полный backend набор, web media tests/build и Swift gates+
Darwin SDK build обязательны. Одна независимая итоговая проверка всей реализации.
Реальные ShareLink, первый показ форм и переходы проверяются затем на iPhone.

Backend меняется в ../.worktrees/pickmatch-link-access, ветка feat/link-only-sharing.
Native-каталог не Git: сохраняем исходный архив и точный diff. Merge/push/deploy,
миграция production и реальная10ГБ-нагрузка не входят в это разрешение.
