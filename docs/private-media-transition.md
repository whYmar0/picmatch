# Переход к защищённой выдаче медиа

Статус: код и локальные/реальные Cloudinary-проверки подготовлены и приняты.
**Пользователь согласовал production-перенос после объяснения backup, защиты
существующих файлов и выкладки. Выполнение ещё не началось: сначала проверяются
доступы и резервная копия.** Повторное согласование того же объёма не требуется.

## Что меняется

Фото, видео и миниатюры альбомов получают адрес `/api/media/<photo_id>`.
Владелец и активный подтверждённый пользователь с SharedAccess получают доступ
к приватному альбому. Публичный альбом доступен без входа. Аватары остаются
публичными, но только при наличии соответствующей записи User.

Нативный клиент может отправлять Bearer-заголовок. Веб-клиент получает разрешение
на конкретный файл и вариант, действующее 300 секунд; JWT аккаунта в URL не попадает.
Разрешение — ограниченная ссылка: скопировавший её сможет читать этот файл до
истечения срока или отзыва прав. Оно не позволяет входить в аккаунт или запрашивать
другие файлы. Выход из приложения локальный, поэтому ранее скопированное разрешение
может работать до истечения 5 минут. Отзыв SharedAccess/блокировка/сброс пароля
проверяются сервером на каждом новом приватном запросе. Содержимое уже полученных
копий и уже начатую передачу отозвать нельзя.

Существующая ссылка общей аналитики может повторно создать SharedAccess после
его удаления. Чтобы закрыть повторный вход по этой ссылке, также поверните
share token. Это прежнее поведение, в этом этапе оно не изменено.

Cloudinary-оригиналы и eager-варианты альбомов должны иметь delivery type
`authenticated`. Подписанный Cloudinary URL используется только сервером.
API передаёт байты, не делает перенаправление. Аватары используют прежний `upload`.
Изображения заранее получают варианты width2048/width500, crop=limit, q_auto,
с сохранением формата; динамический f_auto на authenticated-вариантах не используется.
Локальная миниатюра — WebP до 480 px. Видео поддерживает GET/HEAD/Range и прежний
просмотр миниатюр через метаданные исходного видео.

## Почему нельзя просто выложить новый код

Существующий Cloudinary-файл с типом `upload` остаётся доступным по прежнему URL
в обход API. Новый gateway отказывает для таких альбомных ресурсов с HTTP 503.
Оба новых столбца также должны существовать до запуска нового backend.
Флаг приватности сам по себе не защищает ранее опубликованный файл.

Старые `/uploads/<album-file>` и `/api/thumbnail/<filename>` закрыты. Новый веб-клиент
использует API-адреса. Старую открытую вкладку нужно перезагрузить. Сохранённые
обложки недавних альбомов со старыми storage URL заменяются заглушкой, пока
альбом не будет открыт снова и не запишет актуальный адрес.

В `frontend/vercel.json` домен `https://pickmatch-api.onrender.com` разрешён
для `img-src` и `media-src`. При смене домена API обновить обе директивы
вместе с `VITE_API_URL` и `BASE_URL`, иначе браузер заблокирует медиа.

## Подготовка к отдельно согласуемой миграции

1. На staging повторить локальные проверки и проверить реальный Cloudinary: eager
   изображения, GIF/PNG/WebP, видео, Range и отсутствие unsigned-доступа. Подтвердить
   квоты и дополнительный трафик/нагрузку API: файлы теперь проходят через backend.
   Репетиция самого переноса также выполнена на двух новых синтетических ресурсах:
   PNG и WebM переименованы из upload в authenticated, asset_id сохранён, видео
   совпадает по SHA256, eager-варианты работают. 16 проверок прошли; четыре
   предварительно открытых старых URL после invalidation вернули404 в точке проверки.
   Manifest: игнорируемый `staging/migration-probe.json` рядом с тестовым стендом.
   Это не заменяет проверку реальных старых адресов и распространения CDN при миграции.
2. Подготовить окно обслуживания без новых загрузок/изменений. Сделать резервную
   копию БД и перечень ресурсов. Не публиковать подписанные URL, токены и секреты
   в отчётах. Убедиться, что выбран правильный проект/Cloudinary environment.
3. Инвентаризация без изменений схемы: из backend `python migrate_media_privacy.py`.
   Команда печатает только агрегированные количества, не меняет файлы/Cloudinary.
   Выполнять против production только после отдельного согласования.
4. После backup и согласования добавить столбцы:
   `python migrate_media_privacy.py --apply-schema`. Операция аддитивна и повторяема;
   старым строкам назначается `upload`. Она **не** преобразует Cloudinary-ресурсы.
   Для локального хранилища преобразование файлов не требуется.
5. При Cloudinary сгруппировать Photo и PendingUpload по resource_type/public_id.
   Аватары исключить. Проверить дубликаты ссылок между альбомами и незавершённые
   загрузки; их следует перенести вместе или дать им истечь и выполнить штатную
   очистку до переключения. Не предполагать, что все старые файлы лежат в Cloudinary:
   отдельно сверить конфигурацию и фактическое существование каждого ресурса.
6. Для каждой группы создать новый случайный public_id и сохранить локальный
   закрытый manifest: исходный public_id/type, новый id, asset_id/version, связанные
   строки БД и состояния шагов. Не коммитить manifest. Переименовать через Upload API
   `rename(old_id, new_id, resource_type=..., type="upload", to_type="authenticated", invalidate=True)`.
   Для изображений выполнить `explicit(new_id, type="authenticated", resource_type="image", eager=ALBUM_IMAGE_TRANSFORMS)`
   и дождаться окончания подготовки обоих вариантов. Здесь используется существующий
   SDK; значения преобразований взять из cloudinary_utils.py, не менять их вручную.
7. Только после успешной проверки ресурса обновить `stored_filename` и
   `cloudinary_delivery_type="authenticated"` у связанных строк в одной транзакции.
   Проверять, что старые значения не изменились; обновления идемпотентны по manifest.
   При частичном отказе остановиться и продолжить с записанного шага, не создавать
   дубли и не возвращать приватный ресурс в публичный `upload` ради восстановления.
8. Проверить старые оригинальные и производные URL после CDN invalidation.
   Cloudinary предупреждает, что очистка кэшей распространяется не мгновенно.
   Учитывать URL с версиями/без версий и старые f_auto/thumbnail-варианты.
   Пока старые URL возвращают содержимое, приватность старых публикаций не подтверждена.
9. Проверить, что в Cloudinary-альбомах не осталось `upload`, а eager-ресурсы готовы.
   Затем развернуть совместимые backend и frontend, перезагрузить старые вкладки.
   Приостановка/порядок выкладки должны исключать работу старого клиента с закрытыми
   raw URL. Нативный список этапа 4 совместим, поскольку поля метаданных сохранены.

## Приёмка после согласованного развёртывания

Локальная проверка подготовленного кода: backend **36 passed**, Node **9 passed**,
Chromium **3 passed**, production-сборка успешна (предупреждение об устаревших
данных Browserslist). Независимая проверка исходников не выявила подтверждённых
замечаний. Затем на отдельном локальном стенде с реальным Cloudinary выполнены
218 проверок пяти новых синтетических ресурсов и проверка настоящей веб-галереи:
[отчёт и пользовательские сценарии](private-media-staging.md). Старые публичные
CDN-адреса, реальный iPhone и нагрузка production пока не проверялись.
Проверка смены аккаунта относится к действию внутри приложения; прежняя
синхронизация авторизации между вкладками не добавлялась. Старая ветка ThumbButton
в VotePage может показывать пустую миниатюру видео, если thumb_url содержит видео;
это прежнее ограничение, оставленное без изменения в этапе защиты медиа.

- Приватный файл/миниатюра: владелец и SharedAccess → 200; посторонний/гость → 404.
- Public → private: старый API URL перестаёт работать анонимно, API не кэширует ответы.
- Удалённый share/сброс пароля/заблокированный пользователь: старый ticket не даёт доступ.
- Неверный/просроченный/чужой photo/variant ticket не работает; JWT нельзя использовать
  вместо media ticket и наоборот.
- Аватары публичны; произвольный файл в uploads или thumbnail cache не отдаётся.
- GET/HEAD, перемотка видео и byte ranges работают; повторное обновление ticket не
  сбрасывает время/намерение воспроизведения. Изображения с ленивой загрузкой обновляют
  истёкшее разрешение и сохраняют прежние fallback-обработчики.
- Выход/смена аккаунта очищает DOM-источники и кэш разрешений.
- В ответах/Location нет Cloudinary-подписей и JWT аккаунта. В access-логах/прокси
  нужно скрывать query-параметр `ticket`: это секрет с ограниченной областью/сроком.
- Старые публичные Cloudinary URL действительно закрыты после распространения CDN.

## Восстановление при проблеме

Колонки аддитивны, удалять их не требуется. Предпочтительно остановить доступ и
исправить/продолжить миграцию по manifest. Возврат старого приложения не восстанавливает
raw URLs после смены delivery type и public_id. Не републиковывать приватные файлы
как `upload`. DB backup и manifest нужны для согласованного восстановления связей;
любые обратные операции с Cloudinary требуют отдельного решения.

Источники: [контроль доступа Cloudinary](https://cloudinary.com/documentation/control_access_to_media),
[переименование](https://cloudinary.com/documentation/rename_assets),
[CDN invalidation](https://cloudinary.com/documentation/invalidate_cached_media_assets_on_the_cdn).
