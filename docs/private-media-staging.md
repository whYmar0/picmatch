# Локальная проверка реального Cloudinary

Рабочий Render, production-БД и существующие медиа не используются. Новая проверка
согласована пользователем после завершения локального этапа 5. Выбран отдельный
локальный backend с настоящим Cloudinary.

## Подготовленное окружение

- API: `http://127.0.0.1:8002`.
- Веб: `http://127.0.0.1:5174`.
- Папка состояния: `.planning/2026-11-13-media-privacy/staging/`.
- Внутри: `.env`, отдельная `media.sqlite3`, `uploads/`, `accounts.txt`.
- Эта папка исключена из Git. Секреты и пароли в отчёт не выводятся.
- Созданы три подтверждённых синтетических пользователя: owner/shared/outsider.
  Их email/пароли лежат только в `accounts.txt`. Отправка почты отключена.
- Уже работающие API на 8000/8001 и веб на 5173 не изменяются.

Нужно заполнить только `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` и
`CLOUDINARY_API_SECRET` в созданном `.env`. Брать их из выбранного Cloudinary
environment; [официальная настройка SDK](https://cloudinary.com/documentation/cloudinary_sdks#configuration_parameters).
Секреты в чат не присылать. Предпочтителен отдельный тестовый environment. Если
используется тот же Cloudinary, проверяются только новые синтетические загрузки;
старые файлы не мигрируются и не переименовываются. Проверка расходует небольшую
часть квот загрузки, преобразований и доставки.

## Повторный запуск из уже открытого WSL

Эти команды используют установленный Windows Python/Node из WSL. Установка
новых пакетов не требуется. Два отдельных окна терминала:

```bash
cd /mnt/c/Users/zell/Documents/PythonProjects/project/picmatch_v5/backend
./venv/Scripts/python.exe -m uvicorn main:app \
  --env-file ../.planning/2026-11-13-media-privacy/staging/.env \
  --host 127.0.0.1 --port 8002 --no-access-log
```

```bash
cd /mnt/c/Users/zell/Documents/PythonProjects/project/picmatch_v5/frontend
cmd.exe /d /c "set VITE_API_URL=http://127.0.0.1:8002/api&& npm run dev -- --host 127.0.0.1 --port 5174 --strictPort"
```

Команды предназначены для запуска после остановки соответствующего тестового
процесса. `--no-access-log` предотвращает запись media tickets в access-лог.
При изменении ключей Cloudinary backend нужно перезапустить.

## Проверка после подключения Cloudinary

Сначала автоматическая проверка на новых синтетических PNG/JPEG/GIF/WebP и видео:
реальная загрузка authenticated, доступ через API, изображения/миниатюры, GET/HEAD,
byte ranges, отсутствие unsigned-доступа Cloudinary. Затем owner/shared/outsider/guest,
отзыв доступа, public → private и смена аккаунта в вебе. Синтетические ресурсы
учитываются отдельно; существующие альбомы не затрагиваются.

После успешной автоматической проверки — пользовательские сценарии:

1. Открыть [локальный веб](http://127.0.0.1:5174) на этом компьютере и войти как owner
   по данным `accounts.txt`.
2. Открыть подготовленный приватный альбом: фото, миниатюры и видео должны загружаться;
   видео должно воспроизводиться и перематываться.
3. Открыть тот же альбом как shared: медиа доступны. Как outsider/без входа:
   содержимое приватного альбома недоступно.
4. Переключить аккаунт в приложении: изображения и кадр видео прежнего аккаунта
   очищаются. Это проверка внутри вкладки, межвкладочная синхронизация не добавлялась.
5. Владелец может переключить этот тестовый альбом в публичный режим и открыть
   ссылку без входа: медиа доступны. После проверки вернуть приватный режим.

Подготовленный альбом: **Cloudinary privacy acceptance**. В нём четыре цветных
синтетических изображения и короткое видео. Прямая ссылка для проверки доступа:
`http://127.0.0.1:5174/vote/L2RX0DSLo86XjyPT0eJ8mA`.

Это локальный стенд для браузера компьютера. На iPhone `127.0.0.1` обозначает
сам iPhone; нативная сборка пока использует прежний адрес API. Мобильная проверка
требует отдельного доступного с телефона адреса и не считается выполненной.

## Статус

**Реальный Cloudinary проверен успешно: 218 проверок на пяти новых ресурсах.**

- Через настоящее API выполнены загрузка, PendingUpload → Photo, authenticated
  storage, eager display/thumbnail для PNG/JPEG/GIF/WebP и исходное видео WebM.
- Owner/shared получают приватное медиа; outsider/guest получают 404. Проверены
  scoped tickets, отзыв SharedAccess, public → private, no-store/no-referrer.
- Для видео проверены GET, HEAD, первые байты и suffix Range с точным сравнением.
- Неподписанные Cloudinary URL оригиналов и eager-вариантов закрыты.
- В Chromium без подмены API проверены обычный вход владельца, открытие галереи,
  все четыре изображения, воспроизведение и перемотка настоящего видео.
  Ошибок JavaScript страницы не зарегистрировано.

Отчёт/manifest: `staging/cloudinary-manifest.json`; результат браузера:
`staging/browser-result.json`; снимки `owner-gallery.png` и `owner-video.png`.
В них нет паролей, ключей или media/account tickets. Одноразовый проверочный
сценарий `staging/verify_cloudinary.py` оставлен рядом для изучения; повторный
запуск с существующим manifest намеренно запрещён, чтобы не дублировать ресурсы.
Восемь проверок unsigned eager-вариантов выполнены отдельным продолжением без
дополнительных загрузок и добавлены в тот же manifest.

После проверки альбом оставлен приватным, доступ shared восстановлен. Пять
синтетических Cloudinary-ресурсов сохранены для ручной проверки. Производственные
альбомы/БД/Render не менялись. Инвалидация старых публичных CDN-адресов, реальный
iPhone и нагрузка production не проверялись.

**Ручная приёмка пройдена:** пользователь сообщил, что тесты проходят, и прислал
экран outsider «Альбом не найден или ссылка устарела / Media not found».
Это ожидаемый отказ для приватного альбома; существование альбома не раскрывается.
Проверка принята для локального стенда. Разрешение на production-миграцию/деплой
из этой приёмки не следует.
